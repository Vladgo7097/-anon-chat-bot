# Промт: система звонков 1-на-1 для anon-chat-bot

Готовое задание для сессии, которая будет это строить. Всё, что ниже про текущее
устройство проекта — проверено по коду и по серверу, а не по памяти. Если факт
разошёлся с кодом — верь коду и поправь этот файл.

---

## Задача

Добавить голосовые (с опциональным видео) звонки один-на-один между двумя людьми,
которые уже находятся в активном анонимном диалоге. Звонок доступен **только по
Premium-подписке**. Инициировать можно из веб-версии и из бота; принимать — тоже с
обеих сторон. Сам разговор всегда происходит в браузере: внутри чата Telegram
голосовой звонок между двумя пользователями бота технически невозможен.

## Продуктовые решения (уже приняты владельцем, не пересогласовывать)

1. **Звонки только для Premium.** Проверка у инициатора обязательна. Решить и
   зафиксировать: нужен ли Premium и принимающей стороне — по умолчанию **нет**,
   принять звонок может любой (иначе фича не взлетит: платящих сейчас двое).
2. **Камера выключена по умолчанию.** Включение — только через явное подтверждение
   с честным текстом «собеседник увидит твоё лицо, анонимность будет потеряна».
3. **Вариант «включить с размытием лица»** остаётся — третья кнопка в том же
   подтверждении.
4. **Одностороннее видео допустимо** (один включил, второй нет) — показывать это
   плашкой, не запрещать.
5. **В боте звонок — команда `/call`** плюс сообщение с инлайн-кнопками
   «Принять / Отклонить». «Принять» открывает ссылку на комнату в браузере.

## Архитектура, которую нужно реализовать

### 1. Сигналинг — через существующий WebSocket, без нового сервиса

Добавить в `web/ws.py` новые типы сообщений поверх текущего протокола. Клиент → сервер:
`call_offer`, `call_accept`, `call_decline`, `call_hangup`, `webrtc_offer`,
`webrtc_answer`, `webrtc_ice`. Сервер → клиенту: те же события, доставленные второй
стороне через Redis Pub/Sub `chat:{session_id}` (канал уже есть — не заводить новый).

SDP и ICE-кандидаты просто передаются между сторонами как непрозрачные строки.
Сервер их не разбирает и не хранит.

### 2. Состояние звонка — в Redis, не в PostgreSQL

Звонок живёт минуты, переживать рестарт ему не нужно. Ключ вида
`call:{session_id}` со статусом (`offered` / `active`), участниками и временем
начала, TTL ~2 часа. В PostgreSQL писать **только факт состоявшегося звонка** для
статистики и защиты от абуза — новая таблица `calls` (session_id, initiator,
started_at, ended_at, duration_seconds, end_reason) плюс миграция `013_calls.sql`.
Миграции — forward-only, нумерация по порядку, см. `migrations/README.md`.

### 3. Вход в комнату по одноразовому токену (важно для пользователей из бота)

Человек в боте нажимает «Принять» — у него **может не быть веб-сессии вообще**.
Поэтому ссылка должна быть вида `https://anonim.chat.mooo.com/call/{token}`, где
token — случайный (`secrets.token_urlsafe(32)`), одноразовый, живёт в Redis 5 минут
и хранит пару `(telegram_id, session_id)`. При открытии: токен гасится, выдаётся
обычная cookie-сессия (`web/auth.py::create_session_token`), человек попадает сразу
в комнату. Токен нельзя переиспользовать и нельзя угадать.

### 4. WebRTC и TURN

Медиа — напрямую между браузерами (P2P), сервер в них не участвует. Нужны:
- STUN — можно публичный (`stun:stun.l.google.com:19302`) как дополнение;
- **TURN — свой, обязателен**: без него не соединится заметная доля людей за
  симметричным NAT (мобильные операторы). Ставить `coturn` на этот же сервер,
  порты 3478/UDP+TCP и 49152–65535/UDP (проверено: сейчас свободны).
- Учётные данные TURN — **только временные** (long-term credentials по HMAC от
  общего секрета, TTL ~10 минут), выдаются эндпоинтом `/api/call/ice` авторизованному
  пользователю. Постоянный логин/пароль в JS не зашивать — его сразу же начнут
  использовать как бесплатный прокси.

### 5. Ограничения этого сервера (реальные цифры, проверены)

**1 CPU, 1.9 ГБ RAM (свободно ~885 МБ), 6.5 ГБ свободного диска.** Coturn сам по
себе лёгкий (~30–50 МБ), но релей ест трафик и немного CPU. Из этого следует:
- аудио (~50–100 кбит/с в каждую сторону) — нормально;
- видео (0.5–2 Мбит/с) через релей — дорого, поэтому **ограничить битрейт видео**
  (например 500 кбит/с, 640×480) в SDP/`RTCRtpSender.setParameters`;
- поставить потолок одновременных звонков (например 10) и вежливо отказывать сверх
  него, а не падать;
- на всякий случай ограничить `total-quota`/`user-quota` в конфиге coturn.

## Анонимность и безопасность — обязательные требования

1. **Ни одна сторона не должна узнать telegram_id, username или имя другой.**
   В сигналинге передавать только `session_id` и анонимные `anon_id`.
2. **P2P-соединение раскрывает IP-адреса обеих сторон друг другу** — это природа
   WebRTC. Решить осознанно и записать решение: либо принять (стандартно для
   Discord/WhatsApp-подобных), либо форсировать релей через TURN
   (`iceTransportPolicy: "relay"`) — тогда IP скрыт, но весь трафик идёт через
   сервер и упирается в его канал. **Рекомендация: форсировать релей**, потому что
   продукт про анонимность, а нагрузка при текущих объёмах небольшая.
3. Токен комнаты — одноразовый, короткоживущий, не логировать целиком.
4. TURN-креды — временные, с истечением.
5. Звонок обязан завершаться, если диалог завершён (`chat_ended` уже приходит в тот
   же Pub/Sub-канал — подписаться и класть трубку).
6. Жалоба во время звонка должна работать: кнопка «Пожаловаться» в комнате,
   существующий `services/reports.py`.

## Чего НЕ делать

- Не поднимать отдельный медиасервер (SFU/Janus/LiveKit) — для 1-на-1 он не нужен и
  этот сервер его не потянет.
- Не писать содержимое звонка на диск и не пытаться его записывать.
- Не заводить второй WebSocket — использовать существующий `/ws/session`.
- Не дублировать логику Premium/диалога — только вызовы существующих сервисов.
- Не трогать существующий поток сообщений в `handlers/chat.py` и `services/relay.py`
  сверх добавления новых событий.

## Как проверять

**Юнит-тесты** (обязательно, по образцу существующих в `tests/`, SQLite-фолбэк,
Redis мокается):
- звонок нельзя начать без Premium;
- звонок нельзя начать вне активного диалога;
- второй звонок в том же диалоге не создаётся, пока идёт первый;
- токен комнаты одноразовый: второе открытие — отказ;
- завершение диалога завершает звонок;
- потолок одновременных звонков соблюдается.

**Ручная проверка** (без неё не считать сделанным):
- два реальных Telegram-аккаунта, один в боте, второй на сайте;
- звонок проходит, слышно в обе стороны;
- проверить с мобильного интернета (там как раз симметричный NAT — если TURN
  настроен неверно, соединение не встанет именно здесь);
- камера включается только после подтверждения, размытие работает;
- «Сбросить» кладёт трубку у обоих.

**Прогон тестов**: `python -m pytest tests/ -q` локально (Docker не нужен, см.
«Как гонять тесты быстро» в `AGENTS.md`), потом деплой и проверка логов обоих
контейнеров.
